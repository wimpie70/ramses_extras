## Release blockers

### 1. Published dependency is incompatible

`ramses_cc` still requires `ramses-rf==0.60.4`, but imports pool modules that are absent from the 0.60.4 wheel. <ref_snippet file="/home/willem/dev/ramses_cc/custom_components/ramses_cc/manifest.json" lines="13-22" /> <ref_snippet file="/home/willem/dev/ramses_cc/custom_components/ramses_cc/mqtt_pool_bridge.py" lines="37-43" />

The 0.60.4 wheel was checked directly:

- `callbacks.py`: absent
- `mqtt_pool.py`: absent
- `pooled.py`: absent

A new `ramses_rf` version must be published, then `ramses_cc` must pin that exact version and rerun CI without the editable local checkout.

### 2. Missing root owner breaks acceptance

When the root `_owner` is missing, this comparison becomes `None == None`, incorrectly accepting ownerless candidates:

```python
if entry.get(SZ_TR_OWNER) == root_owner:
```

<ref_snippet file="/home/willem/dev/ramses_cc/custom_components/ramses_cc/coordinator.py" lines="1278-1305" />

Related problems:

- An ownerless candidate can become transmit-enabled.
- An explicitly owned HGI may be rejected.
- `manage_pool_mqtt` can give a device `_owner: me` without writing the root `_owner`.
- Wildcard single-HGI MQTT can produce an accepted set that excludes the effective fallback primary.

These cases have no `ramses_cc` regression tests yet.

### 3. Receive-only candidates still receive `!V`

Although RF frames are now blocked through `PoolChild.accepted`, every configured child—including an ownerless candidate—gets a firmware command when its LWT reports online:

<ref_snippet file="/home/willem/dev/ramses_cc/custom_components/ramses_cc/mqtt_pool_bridge.py" lines="469-479" />

If “receive-only” means no outbound communication before acceptance, `!V` must also be gated.

### 4. MQTT topic parser accepts non-HGI IDs

Topic extraction validates only `NN:NNNNNN`, not the required `18:NNNNNN`. A topic such as `32:153289/rx` could be treated as an HGI and added to the schema as `_class: HGI`.

<ref_snippet file="/home/willem/dev/ramses_cc/custom_components/ramses_cc/mqtt_pool_bridge.py" lines="502-526" />

### 5. MQTT broker/topic form does not match runtime behavior

`manage_pool_mqtt` asks for host, port, credentials, and topic and stores an `additional_ports` URL. <ref_snippet file="/home/willem/dev/ramses_cc/custom_components/ramses_cc/config_flow.py" lines="2096-2144" />

But in the HA MQTT path:

- the entered host and credentials are ignored;
- the additional topic is ignored;
- every HGI uses the primary HA MQTT broker/topic.

With a serial primary, that same URL activates the direct-paho hybrid path, contradicting Phase 1’s “MQTT-only, no paho inside HA” design. <ref_snippet file="/home/willem/dev/ramses_cc/custom_components/ramses_cc/coordinator.py" lines="2257-2324" />

This needs a decision:

- **Recommended Phase 1:** only permit HGIs on the existing HA MQTT broker/topic; configure just the HGI ID.
- Defer different brokers/topics and serial+MQTT pooling to Phase 2.

### 6. Outbound publish outcome is premature

`publish_frame()` schedules `mqtt.async_publish()` as a background task and returns immediately. The pool then reports `WriteOutcome.SUBMITTED` without knowing whether MQTT accepted the publish.

<ref_snippet file="/home/willem/dev/ramses_cc/custom_components/ramses_cc/mqtt_pool_bridge.py" lines="282-324" />

For RF frames, `publish_frame()` should await the HA MQTT publish operation so exceptions reach `write_routed()`.
