# Working Notes

## PWhite-Eng Coding Preferences (from PR 868 review, Jul 20 2026)
When contributing to ramses_rf, follow these architectural standards:
1. **Encapsulation** — no direct private attribute mutation from outside
   the object (e.g. `old_parent._dhw_valve = None`,
   `old_parent.childs.remove(dev)`). State mutation should remain within
   the object itself. Use dedicated methods like `detach_child()` or
   `remove_device()` on the classes so they manage their own referential
   integrity and cleanup.
2. **Type checking** — use `isinstance(old_parent, DhwZone)`, not
   `type(old_parent).__name__ == "DhwZone"`. Or rely on a specific
   interface property.
3. **Separation of concerns** — don't overload factory/retrieval methods
   (like `get_device()`) with complex graph mutation / re-parenting /
   cleanup logic. Keep methods focused on a single responsibility.
   Abstract complex logic into dedicated methods.

### ha-sim Simulator Isolation Prerequisites
**For device_simulator feature to work with automatic isolation:**

1. **MQTT Integration in ha-sim**
   - Must be configured in `configuration.yaml` or UI:
   ```yaml
   mqtt:
     broker: 192.168.40.11 # Replace with your MQTT broker IP
     port: 1883
     username: "your_username" # Replace with your MQTT username
     password: "your_password" # Replace with your MQTT password
   ```
   - Required for MqttEndpoint to subscribe/publish

2. **ramses_cc Config (auto-enforced)**
   - Must use MQTT transport (not serial)
   - Device simulator automatically reconfigures to:
     - Topic: `RAMSES/GATEWAY_SIM/18:001234`
     - HGI: `18:001234` (fake, isolated from production)
   - note: the topic namespace is hardcoded in the simulator code.
   in _rf there is a strict check on prefix `RAMSES/GATEWAY` and also 3 parts divided by '/'
   but we can add the _SIM suffix to the topic to pass the check.

3. **MQTT Broker Permissions**
   - User must have subscribe/publish rights to `RAMSES/GATEWAY_SIM/#`
   - Same broker credentials as production

4. **Port Configuration**
   - ha-sim uses port 8124 (not 8123)
   - Set in `configuration.yaml`:
   ```yaml
   http:
     server_port: 8124
   ```

**Isolation Behavior:**
- Production devices use: `RAMSES/GATEWAY/18:xxxxxx`
- Simulator uses: `RAMSES/GATEWAY_SIM/18:001234`
- Zero crosstalk between namespaces

## PREP: Recipe 32 — Battery (1060) cache restore regression (issue 840)

**Status**: DESIGN ONLY — do NOT edit ha_sim_test.py yet (another thread is working on it).
**Tracked at**: https://github.com/ramses-rf/ramses_cc/issues/840
              ("0.58.3 - Evohome battery states not restoring from cache")
**Originally reported in**: https://github.com/ramses-rf/ramses_cc/issues/822#issuecomment-5011291025
              (peternash: "battery sensors not being cached (or at least only a small
              percentage) and going Unknown again after a period of time")
**Evidence attached to 840**: before/after screenshots + ramses_cc.zip +
              ramses.db.zip from immediately before the restart, plus HA +
              packet logs from after. Confirms: battery states populated
              before restart → Unknown after → up to 24h to recover.

### Root cause (CONFIRMED — same pattern as the 0004/HGI fix already landed)

1. `Code._1060` (device_battery) is in `HIGH_VOLUME_STATUS_CODES`
   (ramses_rf `src/ramses_rf/const.py:165`).
2. 1060 is sent by battery-powered devices only once per day
   (`"lifespan": td(days=1)` in `protocol_schema.py:191`).
3. `_restore_cached_packets` (ramses_rf `lifecycle.py:285-315`) skips any
   cached packet older than 1h that is in `HIGH_VOLUME_STATUS_CODES`
   (`cutoff_dtm = now - 1h`; `if is_match: continue`).
4. ramses_cc keeps cached packets for 24h (`coordinator.py:279`
   `if dt_obj <= now - td(days=1): continue`), so a 2-24h-old 1060 survives
   in the ramses_cc cache but is then dropped by ramses_rf on restore.
5. Result: on restart, the only cached 1060 is almost always >1h old →
   skipped → message_store has no 1060 → `RamsesBatteryBinarySensor`
   state = Unknown. Only devices that happened to send a 1060 within the
   last hour before restart keep their battery reading ("small percentage").

### Fix (mirrors the 0004 fix already in const.py:159-163)
Remove `Code._1060` from `HIGH_VOLUME_STATUS_CODES` in
`/home/willem/dev/ramses_rf/src/ramses_rf/const.py`. 1060 is low-volume
(1/day) and carries semi-static state — exactly the same mis-classification
that caused the 0004 zone-name regression.

### Recipe 32 design (to be appended after Recipe 31 in ha_sim_test.py)

Goal: prove the bug, then prove the fix, by simulating the real-world
"cached 1060 is >1h old on restart" condition. The ha-sim TRV emits 1060
every 13.5s (TRV.yaml), so the bug does NOT manifest naturally — we must
age the cached 1060 timestamps in `.storage/ramses_cc` before restarting.

    # RECIPE 32: Battery (1060) cache restore — stale 1060 must survive
    # =====================================================================
    # Same regression class as issue 822 / 0004 zone names: 1060 is in
    # HIGH_VOLUME_STATUS_CODES but is sent only 1/day, so a cached 1060
    # older than 1h is skipped by _restore_cached_packets on restart and
    # the battery binary sensor goes Unknown.  Tracked in issue 840
    # (with before/after screenshots + ramses_cc.zip from before restart).
    # We force the real-world condition by ageing the 1060 timestamps in
    # .storage/ramses_cc to >1h ago, then restart ha-sim and check the
    # battery entity.
    log_section("Recipe 32: Battery 1060 cache restore (stale >1h, issue 840)")

    # 1. Load mixed profile + activate CTL/TRV/DHW for heartbeats
    await load_profile_yaml(token, _mixed_yaml(), speed=0.01)
    wait(15, "for ramses_cc reload"); token = get_token(); wait(5, "init")
    for dev_id, name in [(CTL,"CTL"),(TRV,"TRV"),(DHW,"DHW")]:
        await ws_send(token, {"type":"ramses_extras/device_simulator/activate_profile_device","device_id":dev_id})
    wait(15, "for 1060 battery packets to populate message_store")

    # 2. Force a fresh 1060 I from TRV (battery 100%, low=0) — payload 006400
    #    schema: ^0[0-9A-F](FF|[0-9A-F]{2})0[01]$  (idx, level, low_flag)
    call_service(token, "ramses_extras", "device_simulator_inject_message",
        {"source_id": TRV, "code": "1060", "payload": "006400", "verb": "I"})
    wait(5, "for 1060 to process")
    call_service(token, "ramses_cc", "force_update")
    wait(5, "for entity state write")

    # 3. Verify the TRV battery binary sensor is ON (battery_ok) before restart
    entities = get_entities(token)
    bat = find_entity_for_device(entities, TRV, prefix="battery_")
    bat_state_before = bat.get("state") if bat else None
    check("TRV battery binary sensor has state before restart",
          bat is not None and bat_state_before in ("on","off"),
          f"state={bat_state_before!r} entity={bat.get('entity_id') if bat else None}")

    # 4. Age every cached 1060 packet to 2h ago in .storage/ramses_cc.
    #    Must stop ha-sim first (HA storage is not safe to write while up):
    #    docker stop ha-sim → rewrite .storage/ramses_cc → docker start ha-sim
    aged_ts = (dt_util.now() - td(hours=2)).isoformat(timespec="microseconds")
    storage = get_ramses_storage()
    packets = storage.get("client_state", {}).get("packets", {})
    n_1060 = sum(1 for p in packets.values() if isinstance(p, dict) and p.get("code")=="1060")
    check("Cached 1060 packets exist to age", n_1060 > 0, f"found {n_1060} 1060 in cache")
    new_packets = {}
    for ts, pkt in packets.items():
        if isinstance(pkt, dict) and pkt.get("code") == "1060":
            new_packets[aged_ts] = pkt   # collapse all 1060 to one aged ts
        else:
            new_packets[ts] = pkt
    storage["client_state"]["packets"] = new_packets
    # stop, write, start
    subprocess.run(["docker","stop","ha-sim"], capture_output=True)
    _write_ramses_storage(storage)  # helper to add: docker cp temp file → /config/.storage/ramses_cc
    subprocess.run(["docker","start","ha-sim"], capture_output=True)
    wait(20, "for ha-sim startup"); log_monitor.reset_baseline(); token = get_token()
    wait(10, "for ramses_cc to restore cached packets + create entities")

    # 5. WITHOUT FIX: battery entity = Unknown (1060 >1h skipped)
    #    WITH FIX (1060 removed from HIGH_VOLUME_STATUS_CODES): state retained
    entities = get_entities(token)
    bat_after = find_entity_for_device(entities, TRV, prefix="battery_")
    bat_state_after = bat_after.get("state") if bat_after else None
    check("TRV battery binary sensor retained state after restart (stale 1060)",
          bat_after is not None and bat_state_after in ("on","off"),
          f"state={bat_state_after!r} (Unknown/None = bug present)")
    # Expected: FAIL on ramses_rf master (bug), PASS after the const.py fix.

## ha_sim_test speed & live feedback improvements (Aug 1 2026)
- Added `HA_SIM_TEST_WAIT_SCALE` env var (default `1.0`) in
  `tools/ha_sim_test/helpers.py` — scales every fixed `wait()`/
  `ctx.wait()` sleep and every `wait_for()` timeout/interval ceiling.
  `ctx.wait()` in `base.py` now delegates to `helpers.wait()` so it
  gets scaling for free. Try `HA_SIM_TEST_WAIT_SCALE=0.5 python -m
  ha_sim_test ...` to see which recipes tolerate faster runs, then
  consider lowering literal `ctx.wait(N, ...)` values in the recipes
  that turn out to be over-conservative (138 fixed `ctx.wait()` calls
  across recipes currently sum to ~730s of pure sleep time — the
  dominant cost in a full single-container run).
- Added `tools/ha_sim_test/dashboard.py` (`LiveDashboard`): live,
  in-place-updating per-container status panes (7 lines each: header
  with current recipe + pass/fail tally + elapsed time, plus 6 lines
  of recent output) during `--parallel N` runs. Attributes stdout
  lines to the correct container via the existing
  `get_current_instance()` contextvar (not by parsing `[name]`
  prefixes), so it works correctly even though asyncio interleaves
  containers at arbitrary points. Auto-disables (falls back to the
  original plain interleaved prints) when stdout isn't a real TTY —
  e.g. piped to a log file — so `> file.log` capture for `grep`-based
  analysis is unaffected. Wired into `run_parallel()` in `parallel.py`.
- Confirmed (by grepping interleaved `>>> Running` markers across all
  4 containers in a full run) that containers genuinely run
  concurrently, not sequentially — despite no explicit
  `asyncio.to_thread`/threading in the codebase. This works because
  some helpers (e.g. `ws_send` over aiohttp) have real `await` points
  that yield control between blocking sections; worth keeping in mind
  since long stretches of pure `ctx.wait()`/`time.sleep()` inside one
  recipe will still stall other containers' progress until the next
  yield point.

### Bug 1: MQTT transport _closing race (R47) — ramses_rf

**File:** `src/ramses_tx/transport/mqtt.py`
**Commit:** dfe929e2 (already committed)

Two changes:
1. `_on_message`: early return when `self._closing` is True. The
   paho-mqtt network thread can deliver messages after `_close()` sets
   `_closing=True` (race during gateway reload). Without the guard,
   stale callbacks log "Transport Error" for every inbound packet.
2. `_close()`: always call `loop_stop()`, even when already
   disconnected. Without this, the network thread auto-reconnects and
   re-subscribes, stealing messages from the new transport.

**Test impact:** R47 goes from TimeoutError (total failure) to
"discovery devices not found in log" (partial pass — a separate
pre-existing issue with `get_discovered_devices` logging).

### Bug 2: PowerState missing from apply_state_update (R32) — ramses_rf

**File:** `src/ramses_rf/entity.py`
**Commit:** dfe929e2 (already committed)

`apply_state_update` handled TemperatureState, DemandState,
ScheduleState, FaultLogState, OpenThermState, HvacState, ZoneState,
but was missing PowerState. The 1060 battery packet restore path sets
`power_state` directly and emits a StateUpdatedEvent, but the event
was silently ignored because no branch matched PowerState. Added:

### Bug 3: resolve_async_attr cooldown blocks R36 setpoint hydration — ramses_cc

**Files:** `custom_components/ramses_cc/helpers.py`, `coordinator.py`
**Status:** uncommitted (working tree only)

The `resolve_async_attr` helper has a 30-second cooldown that prevents
re-dispatching async getters. When R36 injects a 2349 packet (zone
setpoint=21°C), the CQRS ingestion pipeline updates `temp_state.setpoint`,
but the climate entity's `target_temperature` property reads via
`resolve_async_attr(self, z, "setpoint")` which is still in cooldown
from a prior dispatch — so it returns the stale cached value (None or
13.0 from a 2309 heartbeat).

**Fix:** Added `clear_async_attr_cache(entity)` helper in `helpers.py`
that deletes all `_cached_*` and `_cooldown_*` attributes. Called in
`coordinator.async_force_update()` before `async_refresh()`. R36 calls
`force_update` explicitly after injecting 2349.

**Why the entity-level approach doesn't work:** I tried clearing the
cache in `entity._async_update_and_write_state()` (fires on
SIGNAL_UPDATE), but zone entities never receive SIGNAL_UPDATE for 2349
packets. The coordinator fires `SIGNAL_UPDATE_{dto.addr1}` (e.g.
`01:150000` for the CTL), but zone entities subscribe to
`SIGNAL_UPDATE_{self._device.id}` where `Zone.id` =
`f"{tcs.id}_{zone_idx}"` (e.g. `01:150000_03`). These don't match, so
the zone entity's signal handler never fires for 2349 packets.

**Test impact:** R36 climate state passes (state='auto'), but
target_temperature fails (returns 13.0 from 2309 heartbeat instead of
21.0 from 2349). With `clear_async_attr_cache` in `force_update`, the
cache is cleared when R36 calls `force_update`, so the next property
read re-dispatches and picks up the 21.0 setpoint.

## 2026-08-05 — Local MQTT broker + parallel container connectivity fix

### Root cause of parallel container failures

The parallel containers (ha-sim-2/3/4) use **bridge networking** (not
`network_mode: host` like ha-sim), so `localhost:1884` inside those
containers refers to the container itself — not the host.  The local
MQTT broker (mosquitto with `network_mode: host`) listens on the host's
`0.0.0.0:1884`, which is unreachable from bridge containers via
`localhost`.

This caused ramses_cc to fail with "Transport did not bind to Protocol
within 60.0 secs" on all parallel containers, leading to:
- 0 climate entities created (ramses_cc stuck in SETUP_IN_PROGRESS)
- "Simulator not initialized" errors from ramses_extras
- R36, R40, and other recipes failing on ha-sim-2

   instead of `localhost` for instances 2+ (bridge networking).

   `extra_hosts: ["host.docker.internal:host-gateway"]` for hostname
   resolution inside bridge containers.

   HA MQTT integration broker from `localhost` to `host.docker.internal`

### Root cause analysis for all fixed regressions

All regressions were caused by the MQTT "malformed packet" disconnect/
reconnect cycle.  When ramses_cc's MQTT transport reconnects after a
profile reload, the broker sends the retained "online" PUBLISH, then
the client disconnects with "malformed packet".  This causes a 5-10s
window where packets are lost.

The fixes follow two patterns:

1. **Wait for DiscoveryManager before injecting** (R11, R17):
   The fresh_start profile reload triggers a new DiscoveryScan that
   replaces the old one.  If 1FC9 heartbeats are injected before the
   new scan starts, they're detected by the old scan and lost when
   the new scan starts.  Fix: wait for "DiscoveryManager: started"
   in the docker logs before injecting.

2. **Re-inject in wait_for polls** (R24, R28, R36, R40):
   The initial packet injection might be lost due to the MQTT
   disconnect/reconnect cycle.  Re-injecting in the poll function
   ensures fresh data reaches the scan engine once MQTT stabilises.
   Also add sync_topology to force entity re-initialization.

3. **wait_for instead of fixed waits** (R05, R11):
   Convert fixed ctx.wait(N) calls to wait_for() polling with
   appropriate floors to handle parallel load timing.
